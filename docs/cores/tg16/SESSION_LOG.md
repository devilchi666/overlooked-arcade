Production works (loads from `tauri://localhost/` which is same-origin), but dev mode doesn't. **Pivoted to Tauri's built-in asset protocol** (`convertFileSrc()` → `https://asset.localhost/<encoded path>` on Windows). Captured as [[reference_tauri_custom_uri_schemes_blocked_in_dev]] — this gotcha is project-wide and bites anyone wiring custom protocols.
- **Shipped (3) — Thumbnail generation + manual covers.** Added `image = "0.25"` (png/jpeg/webp features). `generate_thumbnail(bytes, dest)` decodes → forces `to_rgba8()` → resizes to 300px wide via `imageops::resize(.., FilterType::Triangle)` → encodes WebP (image-webp backend, lossless). **The RGBA8 conversion is mandatory** — image-webp 0.x errors on palette / grayscale-alpha PNG inputs without it. Manual cover path: `set_manual_cover(romId, systemId, sourcePath)` Tauri command copies user file into `media/covers/<systemId>/<rom_id>.<ext>`, generates thumb, updates MediaDb, persists, emits `oa://media-updated`. Neither `raw.githubusercontent.com` nor `github.com/<owner>/<repo>/raw/<branch>/<path>` resolves Git symlinks server-side — both serve the symlink target as plain-text bytes. libretro-thumbnails uses symlinks heavily (regional renames, beta/final aliases). ## 2026-05-16 (night thirteen) — PCE-CD bringup unblocked: log_interface trampoline

CD games (`.chd` via `mednafen_pce_fast_libretro.dll`) crashed with STATUS_ACCESS_VIOLATION right after the GET_VARIABLE option-poll storm during retro_load_game. Same .dll + .chd + syscard3.pce all worked in RetroArch, so the difference had to be in our environment-callback responses, not the content. With no log_interface wired our oa-shell was running Mednafen silently — fprintf(stderr) is invisible on a Windows GUI subsystem app — which initially made the bug look BIOS-related (the SHA mismatch warning was a red herring; that hash is the dump RetroArch users ship and works fine).

- **Shipped — libretro log_interface trampoline.** New `crates/oa-libretro/build.rs` + `crates/oa-libretro/src/log_trampoline.c` bridge libretro's variadic `void(level, fmt, ...)` log_cb (which Rust can't express on stable — `c_variadic` is unstable) into a normal `extern "C"` Rust forwarder. C side keeps the varargs frame, vsnprintfs into a 2 KB stack buffer, and calls back into `oa_libretro_log_forward` in `state.rs` which routes through `log::{debug,info,warn,error}!` with a `core: ` prefix. `state.rs::cb_environment`'s `RETRO_ENVIRONMENT_GET_LOG_INTERFACE` arm now fills in `(*cb).log = oa_libretro_log_trampoline` and returns true. `cc = "1"` workspace dep added as build-dep to oa-libretro's `Cargo.toml`. `cargo test -p oa-libretro` green (1 doc-test, 0 lib tests); `cargo check -p oa-shell` green.
- **Root cause:** Beetle PCE Fast (and per the libretro source pattern, many Mednafen-derived cores) initialize `log_cb` to NULL when `GET_LOG_INTERFACE` returns false, then call `log_cb(...)` from CD-init paths WITHOUT null-checking. The "access violation" was a NULL function-pointer call, not a Mednafen exception or BIOS verification failure. Returning a valid trampoline unblocked it. HuCard load path doesn't hit log_cb during retro_load_game, which is why Bonk's Adventure worked all along without the trampoline. Captured as [[reference_libretro_log_interface_mandatory]] for future-core bringup.
- **Side fix — `.cargo/config.toml` enabled `linker = "rust-lld"`.** Adding `build.rs` to oa-libretro triggered Windows's classic Git-link.exe-wins-PATH issue when rustc went to link the new build-script binary (`C:\Program Files\Git\usr\bin\link.exe` is a Unix hard-link utility, not MSVC's linker, and it sits ahead of MSVC on the user's PATH). `rust-lld` ships with rustup and is unambiguous. Previous cached build scripts (tauri-build, the retired oa-pce-sys) didn't need to relink so this hadn't surfaced before; will save the next person who adds a build.rs from the same hour of confusion.
- **Almost:** PCE-CD operator validation: Lords of Thunder (.chd) loads and plays end-to-end. Other CD titles in the user's library not yet retested in this session but should all be on the same code path.

Then SGX validation by dropping `mednafen_supergrafx_libretro.dll` + picking it for tg16 in Settings → Cores. Then Phase 3 (shader presets) or open Lynx as system #2.
